# エージェントに良いコードを書かせるガードレール

出典: Lauren Tan（Grok Bot / SpaceXSI）"All Code Is Slop (Except Mine)" https://www.youtube.com/watch?v=O_zcc6Xl12g

## 使いどきろ

- リポジトリをエージェント開発向けに整備するとき
- エージェントが同じミス・悪いパターンを繰り返すとき
- レビュー負荷を下げる仕組みを設計するとき
- ルール文書（AGENTS.md 等）に書き足そうとしているとき — まず仕組み化できないか検討する

## 基本方針：信頼のピラミッド

効く（安くて確実な）順に投資する。

1. コードベース自体（構造・API設計）
2. 静的解析（lint、import禁止、依存グラフ検査）
3. 自動検証（テスト、実行時検証、形式検証）
4. 文章の指示（rules.md、AGENTS.md）
5. 人間のレビュー

上位ほど決定的。指示文と人間レビューは最後の手段。

## 手順

1. **既存コードを掃除する**：エージェントは既存パターンを真似る（コードは記憶）。回避策・非推奨パターンを残すと増殖するので先に消す。
2. **微妙なAPIは禁止してラップ**：useEffectのようにコツが要るAPIは製品コードで使用禁止にし、誤用できない専用APIで包む。説明で教えようとしない。
3. **ディレクトリ構成で境界を表す**：例 electron-main / electron-renderer を分け、またぐimportをlintで禁止。1機能1フォルダ。
4. **その場しのぎを禁止**：setTimeout/requestAnimationFrame等の応急処置を検出・禁止し、lintのエラーメッセージで根本原因へ誘導する。
5. **コメントはほぼ禁止**：エージェントは言い訳コメントで悪いコードを正当化する。不要なmarkdown生成も止める。
6. **修正のたびに仕組み化（黄金律）**：エージェントを一度直したら、lintルール化するか設計変更で同じミスを不可能にする。レビュー項目を減らし続ける。
7. **検証を最重要に**：
   - 実行時検証：機能マップ（共通語彙）と、アプリを操作するCLIを用意しエージェント自身に確認させる。
   - 成果物：スクショ・動画・状態遷移図を人間レビューの代わりにする。
   - 形式検証：TLA+（状態機械・ユーザーフロー）、Lean（アルゴリズムの性質証明）。UIのプロパティベーステスト。
   - 単体・結合・負荷・カオステストを惜しまず書かせる（コストが下がった）。
   - トークン予算の約7割を検証に回す目安。
8. **自動化は信頼ができてから**：低信頼のループを自動化しても雑なコードが速く増えるだけ。土台を固めた後に、ファザー→バグ発見→エージェント修正→PR→自動マージのような外側ループを作る。

## 成果の目安（講演の実例）

10月に1.1万PRマージ、デスクトップ版を毎日リリース、リバート率約0.47%で安定、起動時間・入力遅延・メモリはむしろ改善。

## ボット／スキル運用への応用

- 同じ指摘を繰り返したら、memoryの指示文に足すより、スキル・チェック手順・テンプレートに落とす。
- 結果は自己検証（実際に開く、リンク確認、スクショ）を手順に入れる。
- 定型化と検証ができてからルーティン化（自動化）する。
