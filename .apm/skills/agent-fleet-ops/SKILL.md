# 複数エージェントの運用設計

前提: 1つのインタラクティブセッションで人が逐一プロンプトするやり方は**人間のスループットが天井**になる（Zach Lloyd/Warp）。並列化するなら「人が直接操る」のではなく「人が監督する構造」を設計する。

## 基本構造: manager / builder / reviewer

Untangle（Ryan Carson）の実証パターン — 人は1本の会話だけを持つ:

- **manager エージェント**: 人の唯一の対話相手。チケットの分配・進捗管理・エスカレーション判断を担当
- **builder エージェント**: 1チケット=1セッションで実装。5〜25体程度が管理可能な範囲（それ以上は人間が追えない）
- **reviewer**: builder の出力を採点。builder↔reviewer の往復は**最大3ラウンドでキャップ**し、それを超えたら重要指摘だけ manager に上げる。延々レビュー往復するとマージ待ちコストが膨らむ
- **QA child セッション**: builder とは別系統で動作確認する

## チケット/仕事の与え方

- **1チケット = 1 PR** に揃える: builder が作る変更の大きさを定義し、レビューも1 PR 単位にする（Untangle）
- 依存関係をチケット間で持たせ、manager が「次に始められる仕事」を判断できるようにする
- **巡回は cron で駆動する**: 「定期的に子セッションを確認しろ」とエージェントに頼んでも忘れる。10〜15分間隔のスケジューラから manager を起動させるのが確実（Carson はエージェント任せをやめてスクリプト化した）
- 継続的な仕事は「ジョブ」として渡す: 目標 + 検証手段 + 定期報告までセット（Cognition: 「P99 を改善せよ」→ 計装 → 分解 → 毎日報告）

## マージ・レビュー

- **CIが緑でも trunk は壊れる**: PR は自分のブランチ基点でしか検証されていない。別PRの変更と組み合わせた結果は未検証（Uber）。マージキュー/リベース後再検証が大量PR時代の必須インフラ
- **レビュー滞留は人間側**: AI が PR を機械速度で出しても、マージ判断できる人間の数は増えない（Robinhood）。レビュー負荷の予防: PR を小さく・検証成果物を添付・レビュアー用コンテキストを同梱する
- **PR には「エビデンスパケット」を付ける**: 変更概要・実行した検証とその結果（テスト出力・動作動画）・関連コンテキスト。レビュアー（人/エージェント）が追加調査なしで判断できる形にする（Stephen Chin & Cassandra Chen）

## エージェントの成績管理（Warp Holmes の採点ループ）

エージェントは失敗を隠す（迂回して成功した結果だけ報告する）。定期的に**トレースを採点**する:

1. **証拠を3種集める**: 会話トランスクリプト（依頼+人の修正指示）・ツールコール列（成功までの試行順）・出力 diff（pin したコミット）
2. **ルーブリックで LLM ジャッジ**: 採点基準を Markdown で定義（例: Redundant Test=チーム方針と違う種類のテストを量産、Verbosity=レビュアーが読むコメント/説明の冗長さ、Efficiency=無駄な試行・迂回）。「0.4 以下は要調査」のような閾値を決める
3. **日次で失敗サンプルの共通因を洗う**: 繰り返し出る失敗はスキル/指示書のバグ。該当箇所に具体手順を追記（例:「テスト開始前に空きポートを探せ」で port 推測ループが消えた実例）
4. **スコア推移を記録する**: スキル改訂の前後で平均スコアの変曲点を見る。採点記録はメモリシステムより説明可能

## 環境・隔離

- **セッションごとに使い捨て環境**（Brennan/OpenHands の推奨順位）: K8s セッション等「セッション毎に workspace を作り終わったら捨てる」が最良。壊れた環境が次回のデフォルトになるのを防ぐ。次点は使い捨てコンテナ/GitHub Actions ジョブ。長寿 VM の複数ジョブ同居は認証情報・state プールで最小権限が崩れる
- イベント駆動: GitHub イベント・Slack・監視アラートを起動トリガにする（Actions のスケジュール/PR フックは手軽だが外部 webhook は別途工夫が要る）
- **API キー/認証情報は原則エージェントに渡さない**: 必要最小限のスコープに限定（複数登壇が一致。「ゼロに近いほど良い」）
- エージェントの変更は**回復も試験する**: 外部副作用を含む操作は冪等キー・補償手順を用意（undo-bench: 失敗注入時の回復率47%）

## よくある失敗（Dex Horthy らの警告）

- **レビューなしマージの常態化**（調査: AI PR の30%が未レビューマージ・インシデント増）。工場化 = レビュー構造の強化でもある
- テストを「通す」ことだけを目的化したエージェント（Slopcode Bench で可視化された傾向）— 検証基準を明確に渡す
- エージェントを賢くしようとするオーケストレーターの肥大化（Steve Yegge の失敗談: モデルは勝手に賢くなる。薄いオーケストレーション + 良い環境が本筋）
