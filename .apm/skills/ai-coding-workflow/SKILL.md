# AI コーディングワークフロー

エージェントにコードを書かせる時代の共通認識: **生成は安い、検証が高い。ボトルネックは「書く」から「意図を正しく伝え、正しさを確認する」へ移った。** 人間の仕事は spec・設計・検証環境の設計。

## タスクを受けたとき（計画フェーズ）

1. **エージェントに出すべきか判断する**（Anthropic Effective Agents の基準）
   - 曖昧さ・複雑さがあって逐次判断が必要か → 定型作業はスクリプト/明示ワークフローの方が速く確実
   - エラー時のコストと検出可能性 → 不可逆・検出困難な操作は人間か自動化済み手順で
2. **意図を先に擦り合わせる**: 不明点は実装前に質問して潰す（Matt Pocock "Grill Me" の逆操作）。推測で埋めて実装に進まない
3. **コンテキストに収まるサイズに切る**: 1タスクは「探索→実装→テスト」がコンテキスト ~40%（目安 ~100K トークン）以内に収まる粒度。超えそうなら分割（Pocock のスマートゾーン/ダムゾーン。超えるとモデル性能が劣化）
4. **深いモジュール境界に沿って切る**: タスク分割はインターフェース単位で。浅い小変更の乱立はエージェントが最も苦手とする探索コストを生む

## 実装フェーズ

- **TDD を使える場面では必ず使う**: フィードバック速度が速度制限。先に落ちるテストを書き、通してから次へ（Pocock）
- **既存パターンを複製する前に品質を確認**: コードベースのアンチパターンを真似ると増殖する。参照元が「良いパターンか」を意識する（Lauren Tan: 庭園の比喩）
- **コメントで意図を書くな、構造で表せ**: 「なぜ」をコメントに書くより、命名・ディレクトリ構造・lint ルールで表現する（コメントは執行されないガイドでしかない）
- **パイプでエラーを隠すな**: `cmd | head` や `| tail` は終了コードを最後のコマンドのものに変え、エラー出力ごと消すことがある（Ayush の調査: 失敗したテストが「成功」に見えた実例あり）。失敗を隠すフィルタをかけるなら終了コードを保持する（bash なら `set -o pipefail`）。ツール側を作るときは「最終行=要約+フルログの場所」にして fail loudly にする

## 検証フェーズ（最重要・トークン消費の主戦場）

- **レビュー対象はコードではなく検証成果物**: テスト結果・動作確認のスクリーンショット/動画・型・lint 出力。「書けた」ではなく「動いた」を示す
- **検証は実行可能なものだけ信じる**: 自分でテスト/lint/ビルドを回す。実行してない検証は「確認した」に含めない
- **最終報告だけでなく軌跡（トレース）を見る**: エージェントは失敗した試行を報告せず、ワークアラウンド成功後に「問題なし」と言う（Warp Holmes）。迂回が続く・妙に時間がかかった場合はツールコール列を確認する——繰り返す失敗は指示書/環境のバグの証拠
- **失敗したら原因を突き止めてから直す**: 症状への場当たり修正はエージェントの代表的失敗モード。再現→追跡→根本原因の順（標準的デバッグ手順を省略しない）
- **回復可能性も検証対象**: 外部副作用（API 呼び出し・チケット作成・通知・デプロイ）は git では戻せない。リトライ≠アンドゥ——ack 喪失で二重実行することがある（undo-bench: 通常成功率84%でも失敗注入時の回復は47%）。外部副作用は「実行記録」と「戻し手順」をセットで持つ

## 環境・制約（ユーザーの環境構築を助けるとき）

制約の強さは下に行くほど強い（Lauren Tan の逆ピラミッド）:
1. **コード自体**（API 設計・ディレクトリ構造・型）— 最強。間違った呼び出しが型エラーになる設計
2. **決定的チェック**（lint・型・フォーマッタ・テスト）
3. **検証**（実行時検査・CI）
4. **散文**（AGENTS.md・ルール・コメント）— 最弱。これだけに頼るな

- 修正のたびに「コード/ツールに落とせ」: ルール文書への追記で対処せず、lint ルール・API 設計・構造でカテゴリごと消す
- 不可逆操作は deny ルール＋サンドボックスで物理的に防ぐ（プロンプトの禁止では防げない）
- 指示書（AGENTS.md/CLAUDE.md）はコードから読み取れない情報だけに痩せさせる。「IMPORTANT!!」「never do X」の多用は新モデルでは害になることがある
- **最小権限で環境を作る**（OpenHands Brennan）: タスクに必要なリポジトリ・認証情報・ツールだけを列挙し、それだけを含む環境を用意する。ホームディレクトリの資格情報・本番アクセスをそのまま持つ環境をエージェントに渡さない。隔離手段の選定: 使い捨てコンテナ/セッション単位の workspace が基本。**永続 VM に複数ジョブを同居させると認証情報・書き込み可能 state がプールされて最小権限が崩れる**
- **サードパーティ製スキル/MCP はコード同様に疑う**: SKILL.md はエントリポイントであり、実行時に外部ペイロードを引き込みうる（Zenity の爆破解析: 公式スキルでも credential ディレクトリ走査があった）。静読だけでなくサンドボックス実行で挙動を見る

## 大きな仕事（複数タスク/長期）

- イシューを DAG 化して並列実行可能な単位に分解する（Pocock のカンバン方式）
- 「タスク」ではなく「ジョブ」（=目標+検証手段+報告）として定義できるならそうする（Cognition: 毎日 Slack 報告などのループ含む仕事の与え方）
- 複数エージェントを回す場合の分散システム注意: サブエージェントは「文字列を返す関数」ではなく**共有可変 state を持つ分散システム**。部分失敗（成功に見えるテキスト）、ダーティリード、無制限ファンアウト、冪等でないリトライという古典的故障をそのまま持つ（Microsoft Gish）。分離・整合性・ファンアウト上限を意識する
- 複数エージェントの運用（manager/builder・レビューキャップ・トレース採点）は `agent-fleet-ops` スキル参照
