# Spec 駆動開発

核心（Sean Grove, OpenAI）: コードはエンジニアが生む価値の 10-20%。残りは構造化コミュニケーション。**仕様書が真正の資産で、コードは仕様からの（しばしば不可逆な）射影**。バイブコーディングは「ソースを捨ててバイナリを git 管理している」ようなもの。

## いつ書くか

- 新機能・複数ファイルにまたがる変更・他者（人/エージェント）に委譲する作業 → **必ず先に spec**
- 一行修正・自明な refactor → 不要。spec は投資であり全タスクに要らない

## spec の書き方

- **意図・振る舞い・非目的を書く**: 実装手順ではなく「何が正しいか」。成功条件は検証可能な形（〜できる、〜になる）で
- **条項をID化する**: OpenAI Model Spec のように各条項にIDを振ると、実装・テスト・レビューで参照できる。テストは仕様条項IDに対応付けると抜け漏れが見える
- **コンパイル可能に考える**: 同じ spec からコード・ドキュメント・テスト計画を生成できる構造（用語・入出力・エッジケース）を目指す
- **曖昧語を削る**: 「適切に」「高速に」はリンターにかけるつもりで具体値・判定条件に書き換える

## コードとの関係のルール

- **spec 再生成だけで回さない**（Pocock の批判）: コードを見ずに spec→コードを繰り返すと劣化する。spec は設計の合意ツールであり、コードの品質はコードで維持する
- **変更は spec→実装の順に**: 振る舞いが変わる変更は spec を先に更新し、実装とテストを追随させる。食い違いを放置しない
- **spec もテストする**: 「この spec で X したとき Y か?」という検証プロンプト/テストケースを併記すると、spec が eval・学習素材・レビュー基準として生きる（deliberative alignment の実例）

## エージェントへの渡し方

- spec をタスクのコンテキストとして渡し、実装後の検証は「spec の各条項を満たすか」で採点する
- spec が壊れた/曖昧だった箇所は実装バグではなく spec バグとして直し、次に活かす
